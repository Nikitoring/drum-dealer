# Инструкции для агентов

## Назначение проекта

`Drum Dealer & «Ковры»` — монорепозиторий MVP русскоязычного сайта с двумя направлениями:

- `Drum Dealer` — каталог музыкальных инструментов и оборудования из Японии;
- `«Ковры»` — каталог репетиционных точек, свободных временных слотов и заявок на бронирование.

Текущий MVP не включает корзину, заказ и онлайн-оплату товаров, клиентские аккаунты, CRM/1С, Telegram-бота, автоматические уведомления, мультиязычность и расширенную аналитику. Не добавляйте эти возможности без явного требования.

Основные источники требований:

- [README.md](./README.md) — обзор, стек и команды;
- [docs/requirements/README.md](./docs/requirements/README.md) — фактический scope и критерии готовности;
- [docs/api/README.md](./docs/api/README.md) — публичные и административные API;
- [docs/decisions/README.md](./docs/decisions/README.md) — архитектурные решения;
- [docs/ui/README.md](./docs/ui/README.md) — UI-компоненты и визуальные правила.

## Структура

- `apps/frontend/` — Next.js 15 + React 19 + TypeScript, публичные страницы и админ-панель.
- `apps/backend/` — NestJS 11 + TypeScript, REST API, авторизация, Prisma и миграции.
- `apps/backend/prisma/schema.prisma` — источник истины для модели базы данных.
- `apps/backend/prisma/migrations/` — применяемая история миграций; не редактируйте старые миграции.
- `apps/backend/prisma/seed.js` — тестовое наполнение базы.
- `docs/` — требования, API, решения и UI-документация.
- `docker-compose.yml` — локальный PostgreSQL.

Каталоги `node_modules/`, `apps/frontend/.next/` и `apps/backend/dist/` являются зависимостями или результатами сборки. Их не редактируют и не добавляют в изменения вручную.

## Требования и запуск

Нужны Node.js `>=20.11`, npm и Docker. Из корня проекта:

```bash
cp .env.example .env
npm install
npm run db:up
npm run db:migrate
npm run db:generate
npm run dev
```

Адреса после запуска:

- frontend: `http://localhost:3000`;
- backend: `http://localhost:4000`;
- Swagger UI: `http://localhost:4000/api/docs`;
- health check: `http://localhost:4000/api/health`.

Для тестовых данных:

```bash
npm run prisma:seed --workspace=@drum-dealer/backend
```

Основные команды:

```bash
npm run dev
npm run dev:frontend
npm run dev:backend
npm run build
npm run db:up
npm run db:down
npm run db:migrate
npm run db:generate
npm run check --workspace=@drum-dealer/frontend
npm run check --workspace=@drum-dealer/backend
npm test --workspace=@drum-dealer/backend
```

`check` запускает `prettier --check src/` и ESLint. Перед завершением изменения нужно как минимум форматировать и проверять затронутый workspace; для изменений API, схемы или сборки — дополнительно запускать `npm run build`.
API-тесты backend находятся в `apps/backend/test/` и запускаются Jest + Supertest через `npm test --workspace=@drum-dealer/backend`. Тестовый harness использует in-memory Nest-приложение с моками Prisma и S3, поэтому для него не нужны Docker, PostgreSQL или реальные секреты. При изменении endpoint-ов обновляйте соответствующие успешные и ошибочные сценарии, особенно для POST/PATCH.

## Переменные окружения

Скопируйте [.env.example](./.env.example) в `.env`. Не коммитьте реальные секреты, пароли, JWT secret или ключи S3.

- `DATABASE_URL` должен соответствовать PostgreSQL из Docker Compose.
- `BACKEND_PORT` по умолчанию `4000`, `NEXT_PUBLIC_API_URL` — `http://localhost:4000/api`.
- Для загрузки изображений нужны `S3_BUCKET`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`, `S3_ENDPOINT`, `S3_REGION` и `S3_PUBLIC_URL`.
- `MAX_IMAGE_SIZE_BYTES` ограничивает размер изображения и по умолчанию равен 5 MiB.

## Архитектура и правила разработки

### Backend

Домены расположены в `apps/backend/src/`: `products`, `categories`, `rehearsal-points`, `bookings`, `admin`. Общие механизмы находятся в `common/` (Prisma, JWT guard, storage, пагинация и обработка ошибок).

- Все API-маршруты имеют префикс `/api`.
- Административные маршруты требуют `Authorization: Bearer <JWT>`.
- Валидация глобальная: неизвестные поля отклоняются, типы преобразуются.
- UUID используются как идентификаторы.
- Даты передаются в RFC 3339 с часовым поясом.
- Денежные значения передаются и возвращаются как десятичные строки в RUB.
- Публичное API не должно раскрывать скрытые товары, контактные данные клиентов или другие административные данные.
- Пагинация списков использует `page` и `pageSize`; максимальный `pageSize` — 100.
- Ошибки должны сохранять единый формат `statusCode`, `code`, `message`.

Заявка на бронирование должна создаваться в транзакции с условным переводом слота из `AVAILABLE` в `PENDING`. Это защищает от двойного бронирования при конкурентных запросах. Синхронизация статусов:

- `PENDING → CONFIRMED` переводит слот в `BOOKED`;
- `PENDING → REJECTED` освобождает слот (`AVAILABLE`);
- `CONFIRMED → CANCELLED` освобождает слот (`AVAILABLE`).

Изображения хранятся в S3-compatible storage, а в PostgreSQL — только URL, тип, позиция и связи. Разрешены PNG, JPEG и WebP; для товара и каждого типа изображения репетиционной точки — максимум 10 файлов.

### Frontend

Страницы находятся в `apps/frontend/src/app/`, переиспользуемые компоненты — в `components/`, API-типизация и клиент — в `types/` и `lib/`, серверные обращения — в `services/` и `hooks/`, состояние — в `stores/`.

- Используйте единый API URL из `NEXT_PUBLIC_API_URL`.
- Сохраняйте существующие UI-компоненты и стили; новые элементы сначала проверяйте в [docs/ui/README.md](./docs/ui/README.md).
- Админские страницы должны оставаться защищёнными `AuthGuard` и не показывать административные данные публичной части.
- При изменении API одновременно обновляйте frontend-типы, сервисы/hooks и документацию API.
- Следите за состояниями загрузки, пустого результата и ошибки для публичных и административных запросов.

## Prisma и база данных

Если меняется `schema.prisma`:

1. создайте новую миграцию через `npm run db:migrate`;
2. проверьте, что миграция применяется на чистой базе;
3. обновите Prisma Client через `npm run db:generate` (или через `prebuild` backend);
4. при необходимости обновите seed, DTO, сервисы и [docs/api/README.md](./docs/api/README.md).

Не исправляйте уже применённые миграции и не меняйте базу вручную, обходя Prisma. `prisma migrate reset` допустим только для локальной development-базы и только если это действительно необходимо: команда удаляет данные.

Важное текущее расхождение: основной модуль репетиционных точек создаёт часовые слоты, а legacy-маршрут `/api/admin/schedule/slots` принимает `endAt` и по умолчанию использует 90 минут. Не расширяйте это расхождение; при работе с расписанием учитывайте его и устраняйте отдельным согласованным изменением.

## Проверки перед передачей работы

Для любого изменения:

1. проверьте diff и не затроньте чужие незавершённые изменения;
2. запустите `npm run check --workspace=@drum-dealer/frontend` и/или backend-проверки по затронутому коду;
3. для изменений сборки, маршрутизации, Prisma или общих типов запустите `npm run build`;
4. проверьте вручную соответствующий сценарий через frontend и Swagger/API, если это возможно;
5. в итоговом сообщении укажите изменённые файлы, проверки и известные ограничения.

В рабочем дереве могут находиться незакоммиченные изменения, сделанные пользователем или другим агентом. Не выполняйте `git reset --hard`, `git checkout --`, массовое удаление файлов и не перезаписывайте чужие изменения. Если изменение пересекается с незавершённой работой, сначала разберитесь в diff и минимизируйте область правки.

## Git и стиль изменений

- Делайте небольшие тематические изменения.
- Сохраняйте TypeScript-типизацию и существующие имена доменных статусов.
- Не добавляйте зависимости без необходимости.
- Не коммитьте `.env`, секреты, generated-каталоги и локальные дампы базы.
- При изменении поведения обновляйте документацию рядом с кодом.
